# Global result consistency

The global wrapper can return the permanent epoch's stronger sticky error after
the original core returns a different failure or an optional-allocation fallback.
Three return boundaries previously left `result.startupStatus` holding a different
status. This opt-in successor assigns the exact returned status at each boundary.
The genuine original status stays separately recorded in the epoch.

Only the three final return assignments change. The complete function prefix
through the original core call, including its KERNEL refusal, remains unchanged.
There are no new exports, headers, translation units or admission flags.

The CPU checker authenticates the previous retained-control source/header trees,
1,100 original object rows and 58 project rows per variant. It rebuilds only the
lifecycle implementation and a stronger assertion harness. All unchanged objects
and the explicit privileged-CPU/platform fixtures remain byte-identical. It runs
ten scenarios, all 154 measured constructor allocation failures, two additional
postcore TLS failures and the two terminal controls per variant: 168 positive
cases in plain and fatal ASan/UBSan/function configurations. A separate link with
the legacy lifecycle fails the new result assertion, demonstrating the regression.

`LOCAL-CONTROL-VALIDATION.json` contains the compact receipt. The historical full
runner's failed final-inventory status remains unchanged; these are new controls,
not a relabelled historical pass. The historical compiler executable digest was
not recorded, so this CPU object reuse does not establish native-cache eligibility.

```sh
python3 packages/nvidia-gsp-bootstrap/prospective-global-result-closure/check.py \
  --controls build/retained-construction-controls \
  --composition build/integrated-inputs/compose-check-public \
  --output build/global-result-controls
```

These Linux CPU results do not establish target execution, GPU initialization,
aggregate kernel stack capacity, the PM shutdown deadline or hardware DMA stop.
